§1大方向

你手上是 MacBook Pro 14" M1 Pro（MacBookPro18,3，SoC 代號 t600x），跑 omadora（Fedora Asahi Remix + Hyprland，與 macOS 26 雙系統）， 外接 Apple Studio Display。好消息是 Studio Display 走的是 USB-C DisplayPort Alt Mode，不需要 Thunderbolt tunneling —— 那條路才是真的無解。

這條路上原本疊了兩個斷點，但其中一個已經沒了。 #601 在 2026-09-07 以 completed 關閉 —— 回報者用的是跟你一模一樣的 MacBookPro18,3， 結論是那不是 bug，是 stable kernel 根本沒有 DP alt mode 這條路， 換到 fairydust kernel 之後螢幕就亮了。

所以整個專案的形狀比原本單純：先驗證這個結論在你的機器上也成立（一個下午的事）， 剩下的就只有第二個斷點 —— Studio Display 專屬的 DCP 交握。

2026-09-23 修訂。本頁最初的版本把 #601 當成「t600x 專屬的 atcphy bug」， 整條學習路線都建立在「先解 Bug 1 才看得到 Bug 2」之上。查證 GitHub 現況後這個前提不成立了： #601 已結案、fairydust 的 t600x device tree 早就開好了、#579 也已經有四則討論 （含一位 Asahi 開發者提出、至今沒人做的具體實驗）。§1、§2、§3、§9、§11 都依此改寫。

先分清楚：哪些東西在 Mac 裡，哪些在 Studio Display 裡

這件事最容易搞混，因為兩邊各有一顆 Apple 處理器：

  • DCP（顯示協處理器）在 Mac 裡 —— 負責產生畫面、跟螢幕交握
  • A13 Bionic 在 Studio Display 裡 —— 那是一整顆 iPhone 等級的 SoC，跑 Apple 自家韌體，管面板、USB hub、攝影機、喇叭

斷點 2 就是這兩顆之間的問題：Mac 的 DCP 回報「對面那顆還在睡」（INACTIVE_SINK_DETECTED）， 而 Linux driver 不知道該怎麼回應。所以要「叫醒」的是螢幕裡那顆，不是 Mac 裡那顆。

圖 6 · Mac 與 Studio Display 各有什麼在新分頁開啟，可全螢幕操作 ↗

左邊虛線框內全在 Mac 裡，右邊虛線框內全在螢幕裡，中間那條就是唯一的實體連線。

順帶兩個容易忽略的事實：那條 USB-C 上同時跑影像、USB 資料和電力， 而且電力方向是反的 —— Studio Display 供電給 Mac，最高 96W。 #601 的失敗點正是在「USB3 + DP 混合模式」的切換上，跟線上同時有 USB 資料這件事直接相關。

兩個依然是獨立的，而且分層測試依然是方法論 —— 只是第一層現在預期會直接通過。 普通 USB-C 螢幕會亮、Studio Display 不會亮，就是你要的那條分界線： 它同時確認了斷點 1 已解、斷點 2 是螢幕側的問題。

斷點 2 跟 SoC 無關。#579 的原始回報者用的是 M2 13" MacBook Pro（t8112）， 後來 thejamescollins 在 M1 Max 16"（t6001） 上重現了完全一樣的序列。 兩顆不同世代的 SoC 撞同一面牆，所以問題在 Studio Display 那一側 —— 這也是為什麼 §6 讓 Mac mini 當 target 是合理的：t8103 沒有理由例外。

§2遠中近目標

近程 · 數天～兩週

打底

  • build 出一顆能開機的 fairydust kernel，舊 kernel 留著隨時退回
  • 插一台普通 USB-C 螢幕，確認 #601 的結論在你機器上也成立
  • 用 full-spec 非 Thunderbolt USB-C 線接 Studio Display，把結果貼到 #579（見 §9 第 1 項）
  • m1n1 proxy 模式接通，能從 Python 戳暫存器
  • 讀完 Asahi 的 RE 政策原文

驗收：你有一個「改 → build → 開機 → 看 dmesg」的迭代迴圈， 而且知道自己的機器停在哪一層。

中程 · 數週

學會讀

  • 能在 phy/apple/atc.c 加 printk 並看懂執行路徑
  • 能架起 m1n1 hypervisor，錄下一份讀得懂的 trace
  • 若 fairydust 上還看得到 atcphy_mux_set 的 WARN，拿 PR #503 實測看看有沒有變化 （#622 是被 AI policy 關掉的，測可以，但它的程式碼不能當成你自己的成果送上游）
  • 回報結果 —— 這件事本身就是社群現在缺的

驗收：你看得懂 driver 在對硬體做什麼，也看得懂 trace 在講什麼。

遠程 · 無期限

解題

  • 從 macOS trace 反推 call 20 的正確回應序列
  • 把序列寫成一份別人看得懂的規格，貼進 #579
  • 照規格寫 C，成果送 PR（前提見 §7）

驗收：螢幕會亮。但真正的收穫是你不再怕任何一顆沒有文件的晶片。

階段 0 · build 一顆 fairydust kernel

環境：裝好的 Asahi Linux ｜ 產出：迭代迴圈

USB-C 出圖的程式碼還沒進正式 kernel，在 fairydust 分支上。 不用重裝系統 —— kernel 只是一個 package，你多裝一顆並存，開機時選。

  1. clone fairydust 分支
  2. .config 一定要從現在的 kernel-16k config 起手。 Apple Silicon 上 16K pages 是必需的，這是最容易踩的坑
  3. 開啟 DP alt mode 相關選項，建議編成 module（方便用 dmesg 確認有沒有載到）
  4. build kernel 加 DTB —— Asahi 靠 device tree，別只裝 vmlinuz
  5. 確認 GRUB 選單會顯示（Asahi 預設會跳過），否則你沒地方選回舊 kernel
可能不用自己來 —— 而且它的支援表上就有你的機型。 bharambetejas/asahi-fairydust-display 是針對 Fedora Asahi Remix 的一鍵腳本， 支援表把 MacBook Pro M1 Pro 標成「Tested by community」。 它會處理相依套件、Rust、GPU driver、DP alt mode 模組、DTB、m1n1、GRUB、typec 模組自動載入， 還附一個 hotplug 腳本。需要 15GB 空間、60～90 分鐘。

它的 README 也獨立寫了同一件事：「Plug adapter into the FRONT-MOST USB-C port」 —— 跟 dts 裡的 USB-C Left Front 對得上。

它預設會多打一個 patch（修內建 HDMI 在 suspend/resume 後不亮）， 想要原汁原味的分支就 SKIP_PATCHES=1。
讀過腳本之後的三件事。
  • 材料只有 .config 來自本機。原始碼是 git clone AsahiLinux/linux --branch fairydust --filter=blob:none（約 3GB）； .config 則是 cp /boot/config-$(uname -r) —— 所以 16K page 那個坑它自動幫你避開了
  • README 的第 9 步不會跑。main() 裡 setup_display_script 是註解掉的，註解寫「causes login loop on KDE/Wayland」。 對 Hyprland 使用者是好消息 —— 那段會寫一個用 xrandr、 還硬寫死 2560x1600 的腳本（14" 是 3024x1964）， 外加 XDG autostart 和一條 RUN+= 跑 sleep 2 的 udev rule。全部不會發生
  • 它改 GRUB 的那行對你是空轉。它用 sed 's/GRUB_TIMEOUT_STYLE=.*/…/'，只改既有的行； /etc/default/grub 裡沒有這一行的話什麼都不會發生，要自己加
dts 不用 cherry-pick 了。fairydust 分支的 arch/arm64/boot/dts/apple/t600x-j314-j316.dtsi 第 12 行就是 #define ENABLE_DCPEXT_TYPEC，無條件打開；往下 typec1 已經接上 displayport = <&dcpext1>。 也就是 PR #476 想做的事，fairydust 本身就有了。

而且只有一個孔有 DP。那個 connector 的 label 是 "USB-C Left Front" —— 左側靠前那一孔，走 atcphy1。 #601 的回報者也獨立講了同一件事（「only one port carries DP」）。 其餘的孔插了不會有反應，這不是故障。 順帶：atcphy3 在 dts 裡註明 ATC3 is used for DisplayPort -> HDMI only，那是內建 HDMI 孔的專用路徑。
#601 回報者的具體作法（Arch/omarchy，M1 Pro 14"，可直接對照）：
  • .config 直接拿現在跑的那顆（/proc/config.gz）， 他確認需要的符號本來就都開著：CONFIG_DRM_APPLE、CONFIG_PHY_APPLE_ATC、 CONFIG_PHY_APPLE_DPTX、CONFIG_MUX_APPLE_DPXBAR、CONFIG_TYPEC_DP_ALTMODE
  • 裝成獨立的並存 package，stable kernel 留在 GRUB 當退路
  • 冷插比熱插可靠 —— 開機前就把螢幕插著
每次官方 kernel 更新，都會把 /boot/dtb 搶回去 —— 這是最容易中招的一點。

Fedora 的 /usr/lib/kernel/install.d/10-devicetree.install 在每次 kernel add 時會無條件做這件事： 
rm -f /boot/dtb
ln -s dtb-$KERNEL_VERSION /boot/dtb
它掃的是 /boot/dtb-*（連字號）， 而 make dtbs_install 把 fairydust 的 DTB 裝到 /boot/dtbs/<版本>（複數、斜線）—— 兩者對不上，所以 fairydust 的 DTB 對那支 hook 是隱形的。 緊接著 15-update-m1n1.install 會跑 update-m1n1 把官方 DTB 刷進去。

結果：omarchy update 帶進一顆新官方 kernel 之後， 你的 fairydust kernel 會帶著官方 DTB 開機 —— ENABLE_DCPEXT_TYPEC 那些節點不見了，外接螢幕安靜地不再亮。 症狀是「明明沒動什麼，某天就壞了」。

檢查與修復： 
readlink /boot/dtb          # 指到 dtb-…asahi… 就是被搶走了
sudo ln -sfn /boot/dtbs/<fairydust 版本> /boot/dtb
sudo update-m1n1
值得做成 omarchy 的 post-update hook，跟你其他那幾個放在一起。
另外兩件關於 omadora 的事。
  • installonly_limit 管不到它。 那個限制只作用在 RPM 標記為 installonly 的套件；腳本走的是 make install， 裝出來的不是 RPM，dnf 不會把它擠掉。 （會被擠掉的是最舊那顆官方 kernel。）
  • omarchy update 不會幫你重 build fairydust，上游有新 commit 要自己重跑
它動到的全域設定只有一個，而且退回 stable 也吃得到。 就是上面那個 /boot/dtb + update-m1n1 —— m1n1 之後每次開機都帶著 fairydust 的 device tree，包括你在 GRUB 選回官方 kernel 那次。 其餘（模組、DTB、vmlinuz、initramfs）都帶 -fairydust 後綴並存，不覆蓋任何東西。

repo 裡的 asahi-fairydust-uninstall.sh 會把這些全部還原， 包含把 /boot/dtb 指回官方版本再跑一次 update-m1n1。 它會擋你在 fairydust kernel 裡執行，要先重開機回官方 kernel。

階段 0.5 · m1n1 proxy 的 Python REPL

環境：target 進 proxy 裸機模式 + host 跑 Python ｜ 產出：對 MMIO 的直覺

m1n1 proxy mode 是一個跑在裸機上的 Python REPL： target（Mac mini）什麼作業系統都沒開，host（MBP）用 Python 隔著 USB 線直接讀寫它的暫存器。 m1n1/hw/*.py 裡有一堆現成的暫存器對照表類別。 

export M1N1DEVICE=/dev/ttyACM0   # host 是 Linux（你的 MBP）
                                 # host 若是 macOS 則為 /dev/cu.usbmodemP_01

p.read32(addr)
p.write32(addr, val)

讀 device tree 找到一個 block、從 Python 戳它的暫存器、看硬體有什麼反應。 沒有別的東西能這麼快建立「軟體到底對硬體做了什麼」的直覺。

這裡開始有兩套環境，從第一天就要分清楚：
① proxy 裸機模式（mini 當 target，這時候它上面沒有任何作業系統在跑）
② 裝好的 Asahi（MBP，寫 driver、測 driver、順便當 host 看 trace）

階段 1 · 讀 driver

環境：裝好的 Asahi ｜ 產出：讀得懂程式碼

在現有 driver 加 printk，看它實際跑到哪一行。目標檔案兩個：

  • drivers/phy/apple/atc.c —— Type-C PHY，直接讀寫實體暫存器，中間沒有魔法。 對「想搞懂硬體到 kernel 那段空白」的人來說，這是教科書等級的清楚
  • drivers/gpu/drm/apple/ —— DCP 的 mailbox RPC，抽象好幾層，晚一點再啃

階段 2 · 先 trace 簡單的裝置

環境：m1n1 hypervisor ｜ 產出：讀得懂 tracer 輸出

架起 hypervisor（做法見 圖 3 與 §6），但第一次別碰 DCP。 先找一個簡單的裝置錄一份 trace，把「這串輸出在講什麼」搞清楚。

階段 3 · 轉接頭雙邊 trace　← 整條路的脊椎

環境：m1n1 hypervisor ｜ 產出：一份「正確長相」的 DCP 對照組

插一個便宜的 USB-C → HDMI 轉接頭，在 macOS 和 Linux 兩邊都錄 trace，然後 diff。

關鍵在於：這是一個你知道正確答案的案例。macOS 那邊會動、Linux 這邊不會， 差異就是答案 —— 你不會卡在「我看不懂這段是對是錯」。

要用轉接頭，不要用內建 HDMI 孔。 內建 HDMI 走獨立的 DP→HDMI 轉換晶片（在 t600x 的 dts 裡是 atcphy3 專用）， 它的 DCP 對話形狀跟 Type-C 路徑不一樣。 轉接頭走的才是同一條 atcphy → dcpext → dptx，只是少了那顆 A13。
這一步有人做過了，而且成功。thejamescollins 在 M1 Max 16"（apple,t6001）上 插 Apple USB-C Digital AV Multiport Adapter 轉 HDMI， 在 Hyprland 下跑到 4096x2160@60（#579 的 2026-09-04 留言）。

值得注意的是他的 dmesg：頭兩次還是走了 oob_hotplug status:0x2 → acking unhandled call 20 → dcp_dptx_disconnect， 第二次之後才出現 atcphy_mux_set 的 WARN，然後自己恢復並走進 oob_hotplug status:0x1 → dcp_dptx_connect。 也就是那個 WARN 不必然致命 —— 這正是你要拿來當對照組的「正確長相」。

階段 4 · Studio Display

環境：m1n1 hypervisor + driver ｜ 產出：斷點 2 的答案

掛上 trace_dcp.py、開 macOS、插上 Studio Display，在 proxy 終端找 call 20（DPTX_APCALL_INACTIVE_SINK_DETECTED）， 看 macOS 回了什麼、接下來的幾十筆 message 是什麼順序。

第一次的目標不是解決問題，是確認「call 20 有被錄到」。 錄得到，剩下就是讀懂序列；錄不到（例如 macOS 在 hypervisor 下走了別條路），那是另一個要先解的問題。

在這之前有一個更便宜的實驗，而且是 Asahi 開發者親自點名的。 chadmed 在 #579（2026-08-29）要求用「非 Thunderbolt 的 full-spec USB-C 線」重測 —— 不要 Thunderbolt 線，也不要充電線。回報者當時手上沒有那種線，到今天還沒有人做。

你有 Studio Display、有機器，缺的只是一條線。這件事不用 build kernel、不用 m1n1、不用裝第二份 macOS， 卻可能直接改變 #579 的診斷方向 —— 因為 james 用充電線（USB 2 控制組）時， 螢幕的 USB hub 反而正常列舉了，線材差異在這個 bug 裡顯然還沒被排除。

一個未知數：「叫醒 A13」未必全在 DCP 這條路上，也可能有一部分走 USB-PD（tipd）， 也就是修改點可能橫跨兩個 driver。這件事 trace 出來的第一天就會知道。

§4開機鏈：每個角色在做什麼

m1n1初始化硬體、產生 device tree。Asahi 安裝時就放進 stub 分割區了
U-Boot把 Apple 的特殊開機環境轉成標準的 Linux 開機介面
GRUB讀開機項目清單、顯示選單、把你選的那顆 kernel 載進記憶體
Linux kernel掛載 rootfs、載入模組，最後交給 systemd → Hyprland

kernel 是一組帶版本後綴的檔案

所以多顆可以並存 —— 裝新的不會蓋掉舊的：

/boot/vmlinuz-<版本>              # kernel 本體
/boot/initramfs-<版本>.img        # 開機用的暫時根目錄
/boot/dtb-<版本>/                 # device tree（Asahi 必要，別忘了裝）
/lib/modules/<版本>/              # 驅動模組

那份「有哪些 kernel 可以選」的清單

Fedora 用 BLS（Boot Loader Specification）：一顆 kernel 一個設定檔。

ls /boot/loader/entries/     # 每個 .conf 就是選單上的一項
sudo grubby --info=ALL       # 人話版：列出每一項的 kernel / initrd / 參數

裝完 fairydust 之後這裡會多一項 —— 那是「有沒有裝成功」最直接的驗證，比重開機試快得多。

動手 build 之前，先讓 GRUB 選單顯示出來。 Asahi 預設會跳過選單（為了開機快）。編輯 /etc/default/grub， 把 GRUB_TIMEOUT 設成 5，同時確認 GRUB_TIMEOUT_STYLE=menu —— 只改 timeout 而 style 還是 hidden 的話選單照樣不會出現。 然後 sudo grub2-mkconfig -o /boot/grub2/grub.cfg。

不先做這件事，新 kernel 開不起來時你會找不到地方選回舊的。

m1n1 不是要新裝的東西

它現在就在你的開機鏈裡，每次開機都在跑 —— 沒有它 Asahi 根本開不起來。 之後要做的不是安裝新程式，而是讓同一支程式換個模式：

模式做什麼
平常（你現在）初始化硬體 → 交棒給 U-Boot → 一路到 Linux
hypervisor（之後）進 EL2、攔截 MMIO、把 macOS 當 guest 開起來

實務上會有兩份 m1n1 並存：stub 裡那份繼續負責開你的 Asahi； hypervisor 用的是你自己 build 的新版（官方文件強調「每次都先 chainload working tree 的 m1n1」）。 兩份互不干擾，正常開機流程不受影響。

階段 A · 一次幾秒

研究（Python，在 host 上）

改 tracer → 重跑 → 再看。目的是找出答案。

實作（C，在 kernel 裡）

改 C → build → 重開機 → 看 dmesg。目的是讓 Linux 真的會動。

把 call 20 從現在的「盲目 ack」換成照序列做事的 handler， 位置在 drivers/gpu/drm/apple/。

中間那個交接點才是重點

階段 A 的產出不是程式碼，是一份規格，大概長這樣：

DCP 送 call 20 之後，macOS 回了 ⟨某個值⟩，接著依序做了 A、B、C，然後 link training 才開始。

這份文字有三個用途：你自己照它寫 C、貼到 #579 讓別人能接手、 以及它本身就是 clean room 的標準結構（觀察 → 寫規格 → 照規格實作，你只是一個人扮兩個角色）。

先在 Python 階段把事情弄清楚，再動 C。 帶著一半的猜測去改 kernel，你會把大量時間花在等 build 上。

斷點 1 連階段 B 都不用。 它現在只是「換一顆 kernel」—— 沒有要改的 C，沒有要 cherry-pick 的 patch。 所以整份計畫裡唯一真正要寫程式的，只有斷點 2，而它必須先經過階段 A。

這也讓原本「先拿一個答案已知的題目練手」的設計少了一題。替代的練手題是階段 3： 轉接頭在 macOS 和 Linux 兩邊都會動（james 已經證明了）， 所以那是一個你知道正確答案、可以用來校準自己閱讀 trace 能力的案例。

  • mini 當 target：斷點 2 是螢幕那一側的問題 —— #579 在 t8112（M2）上報，thejamescollins 在 t6001（M1 Max）上重現， 兩顆不同世代的 SoC 撞同一面牆，t8103 沒有理由例外。 插上 Studio Display 就是一個乾淨的測試台

捕獲在 target，解讀在 host

m1n1 的 hypervisor 是 Python 驅動的：target 上攔到事件後透過 USB 回報給 host， 由 host 上的 Python 決定怎麼解讀、要不要放行。所以 -m proxyclient/hv/trace_dcp.py 掛的那個模組，是在 host 上執行的。

這表示你之後要加解碼邏輯是在 host 上寫 Python，不是在 target 上改 C —— 也就是 §5 說的那個快迴圈。

怎麼分辨是 kernel 的問題還是 Hyprland 的問題

你的 MBP 跑 Hyprland，這會製造一種很容易誤判的情況：kernel 其實已經把螢幕接起來了，但畫面就是沒出來。 這不是假設 —— PR #622 的作者就留了這個已知問題： 「重新接上之後，userspace 沒有對 BAD link status 做出反應，要手動 toggle output」。那是合成器層，不是 kernel。

所以每次測試都照這個順序查，對應圖 1 的層次：

# ① kernel 有沒有看到這個接頭？
ls /sys/class/drm/
cat /sys/class/drm/*/status          # connected / disconnected

# ② 有沒有拿到 mode？
cat /sys/class/drm/card*/*/modes

# ③ 合成器有沒有接手？
hyprctl monitors all
wlr-randr

# ④ 底層在講什麼
dmesg | grep -iE 'dcp|atcphy|tipd|typec|altmode'
① connector② modes③ Hyprland結論
disconnected——卡在斷點 1（atcphy，訊號沒出去）—— 先確認你用的是 fairydust、插的是左前那一孔、而且是冷插
connected空的—卡在斷點 2（DCP 沒給 mode）
connected有 mode沒看到Hyprland 的問題，kernel 那邊其實通了

第三種情況是好消息 —— 代表你已經穿過兩個 bug 了，剩下的是 userspace 設定。

版本規則：真正擋人的是「出廠版本」

一個常見的誤解（我也搞錯過）：以為不能裝比目前韌體舊的 macOS。實際規則是——

任何 Mac 都不能開機於比它「出廠時那一版」更舊的 macOS。 而在 Recovery 裡對一個獨立的 volume group 安裝舊版時，韌體不會被改動。
機器出廠版本裝 14.8.3
MacBook Pro 14" M1 Pro（2021）macOS 12 Monterey✅ 可以
Mac mini M1（2020）macOS 11 Big Sur✅ 可以

所以你現在跑 macOS 26 不影響這件事，兩台都在範圍內。 兩個要注意的：

  • 第二份 macOS 需要完整的 volume group（System + Data + 配對的 Recovery，獨立 container）， 不是在現有 container 裡多切一個 volume
  • 選 14.8.3 不要選 13.5。文件兩個都列，但新版 macOS 裝的安全性變更「可能影響使用明顯更舊版本的能力」。 14.8.3 離現在近、風險小；真出問題 13.5 還在後面當備案
韌體版本會影響你看到的症狀。
  • 你的 DCP 韌體來自 macOS 26；#579 的回報者跑的是 7.1.6.fairydust 時期的組合
  • DCP 的協議會隨韌體版本改變（driver 裡有針對不同版本的 struct layout）
  • 你的 Studio Display 韌體也跟別人未必同版

#579 是 2026-08-24 開的，james 的測試一路做到 2026-09-04 —— 資料其實很新，不是陳年舊案。但版本組合仍然人人不同，所以比對時要一併記下版本， 別只貼 dmesg。

怎麼架起來

這不是虛擬機。macOS 跑在 target 真正的 Apple Silicon CPU 上，原生速度、真的硬體； m1n1 待在 EL2，只把幾頁 MMIO 設成 trap，攔下來記錄再放行。macOS 本體不用改。 完整的角色分配見 圖 3。

在 target（Mac mini）的 1TR Recovery Terminal 裡（對測試 volume 做）

csrutil disable        # 關 SIP
nvram boot-args=-v
kmutil configure-boot -c build/m1n1.bin --raw --entry-point 2048 \
  --lowest-virtual-address 0 -v /Volumes/macOSTest

取得 macOS kernel

/System/Volumes/Preboot/[UUID]/boot/[hash]/System/Library/Caches/com.apple.kernelcaches/

在 host（MacBook Pro）上跑

§7規矩（決定你的成果能不能上游）

Asahi 有三份政策要遵守：Code of Conduct、Copyright and Reverse Engineering Policy、 Generative AI Policy。第二份才是真正規範你日常工作的，動手前務必自己讀原文。

工作守則

觀察硬體行為　→　自己理解　→　自己寫　→　送 PR

這條路徑同時滿足法律安全與政策合規，而且也是最快的。原因：

  • 載入 Apple firmware 原封不動跑 ✅ —— 你買 Mac 時就取得授權，沒有複製、沒有散布。 Asahi 從不散布 firmware，是從你自己機器的 macOS 抓的
  • 觀察行為、自己寫實作 ✅ —— 觀測到的是事實，事實不受著作權保護
  • 反編譯 Apple driver 來改 ❌ —— 衍生作品；而且 Linux 是 GPL，你無權重新授權
LLM 的界線（含我）。 Asahi 的 Generative AI Policy 是禁令，不是揭露制度 —— 說明手法只影響罰則輕重，不影響允不允許。而且政策裡點名 「用 LLM 解讀 m1n1 hypervisor 的 trace」會收到警告。 PR #622 就是因此被關掉的，不是技術問題。

這是單向門：一旦透過這個管道學到那段機制，沒辦法事後洗掉再乾淨地貢獻同一份成果。 所以守得住的規則是 —— 別把 trace 內容貼進 LLM，讓那份資料根本沒進到模型的 context。 通用機制（DP link training、mailbox RPC 概念、工具怎麼用）可以問；「我錄到這段是什麼意思」不要問。

政策管的是對 Asahi 的貢獻，不管你在自己機器上跑什麼。 只想修好自己的螢幕、不打算上游，這個限制完全不存在。

§8材料清單

硬體

  • MacBook Pro 14" M1 Pro（MacBookPro18,3，t600x）—— host， 跑 python proxyclient，同時是最終要修好的那台。 host 只需要能跑 python 和認到 USB 序列裝置；官方文件是以 host OS（macOS / Linux） 區分裝置節點名稱，沒有對 host 的 CPU 設限。你的 host 跑 Linux，所以裝置是 /dev/ttyACM0。

  • host ↔ target 的 USB 線：先試 Apple 原廠 USB-C 充電線（C-to-C，不要用 Thunderbolt 線）； 不順就換 USB-C→USB-A（m1n1 文件建議這種，插 host 的 USB-A 孔）
  • 一條 full-spec 非 Thunderbolt 的 USB-C 線 —— 接 Studio Display 用，優先度最高。 chadmed 在 #579 點名要這種線的測試結果，至今沒人做得出來（回報者手上沒有）。 不要 Thunderbolt 線、不要充電線；要標示支援 USB 3.2 / DP Alt Mode 的全規格線。
  • ThinkPad X1 Gen 9（可選的 host）—— host 是純終端機， x86 和 arm64 沒有差別，Asahi 開發者多數就是用 x86 Linux 當 host。 唯一差別是編譯 m1n1 要裝交叉編譯器（gcc-aarch64-linux-gnu）， 而在 Mac 上一樣要裝裸機工具鏈。用它當 host 可以把 MBP 空出來當日常機。 注意：萬一 target 需要 DFU revive，那只能用 Mac 做。
  • 一台「笨」螢幕 —— 用來確認「斷點 1 在你機器上真的沒了」，也是階段 3 的對照組。
    建議挑同時有 USB-C（DP Alt Mode）和 HDMI 輸入的： USB-C 那孔驗證 fairydust 的 DP 路徑，HDMI 那孔測內建 HDMI 在 macOS 26 韌體下還會不會動，平常還能當第二螢幕。
    • 必要：USB-C 輸入要標明支援 DP Alt Mode（有些 USB-C 孔只供電或只傳資料）
    • ❌ 避開 DisplayLink：它走 USB 資料由 CPU 算圖，完全繞過 DP 路徑 —— 可能真的會出圖，但你什麼都沒測到，還會誤判 DP 路徑已經通了
    • ❌ 不要 Apple 的顯示器：有內建處理器就會觸發斷點 2，失去當對照組的意義
    • ❌ 沒有「Thunderbolt 專用」這種規格，買普通的就好
    • 加分：#601 的回報者就是用 ARZOPA Z1FC 16"（純供電模式）在 M1 Pro 上成功的。 買同一台，等於直接複製一個已知會成功的實驗
  • 替代方案：USB-C → HDMI 轉接頭 + 現有的電視，最便宜，一樣避開 DisplayLink
  • 外接 SSD（選配）—— 放測試用的 macOS volume，不佔內建空間

§9現在就能做的事

所有跟螢幕有關的測試都要先有 fairydust。 stable kernel 上根本沒有 DP alt mode 這條路 —— 連 DP-1 這個 connector 都不會出現， 插什麼都不會有反應。所以階段 0 是唯一的入口，沒有捷徑。 下面第 1 項可以現在就做（等貨要時間），但它的測試要等第 2 項完成。
  1. 先下單一條 full-spec 非 Thunderbolt 的 USB-C 線（不要 TB 線、不要充電線）。 Asahi 開發者 chadmed 在 2026-08-29 於 #579 要求這個測試， 原回報者手上沒有那種線，到今天還沒有人做。 線在路上的時候剛好可以 build kernel。
  2. build fairydust，插一台普通 USB-C 螢幕，確認 #601 的結論在你的 MacBookPro18,3 上也成立。記得插左前那一孔、開機前就插著。 會亮，斷點 1 對你就不存在了；不會亮，那才是真的有一個 t600x 專屬問題， 而且你會是第一個有明確反例的人 —— 這時候才值得回 #601 補一則。
  3. 用那條線接 Studio Display，把結果貼進 #579 —— 不管會不會亮都要貼，dmesg | grep -iE 'dcp|atcphy|oob_hotplug' 全貼， 連同 kernel 版本、fairydust commit、線材型號。 這是目前整個 issue 上投入產出比最高的一件事。
  4. 去 omadora 的「External monitor discussion」看一圈、留個言。 那裡的人跟你同樣的發行版、同樣的合成器、同樣的硬體家族， 比 Asahi 主 repo 更可能已經有人踩過你要踩的坑 （malik-na/omadora）
  5. 測一下 MBP 的內建 HDMI 孔現在會不會動。 feature matrix 對 14/16" 的註記是「13.5 FW only」，而你跑 macOS 26 韌體 —— 兩分鐘就有答案，不管結果是什麼都是有用情報
  6. 自己讀一遍 Copyright and Reverse Engineering Policy 原文
  7. 在 target（Mac mini）上開一個完整的 volume group，裝 macOS 14.8.3（見 §6）
  8. host（MBP）上 clone m1n1，確認 proxyclient 跑得動、USB 線接得通

前三步都不用寫一行程式碼，卻是整份計畫裡最快能換到情報的部分。第 4 到 7 項可以跟 build 平行做。 別再往 #601 貼自我介紹了 —— 它已經關了。要打招呼就在 #579。

§10名詞表

這個專案橫跨磁碟、開機、kernel、晶片四個層次，名詞會一直冒出來。 這裡只收會重複出現的，每條一句話，附上「跟這個專案有什麼關係」。

磁碟與分割

名詞是什麼跟你的關係
分割區硬碟上切出來的一塊空間，大小固定—
APFS container分割區裡的一大塊硬碟空間，裡面的 volume 共用它、不用事先切死大小裝第二份 macOS 時會建一個新的
volumecontainer 裡的一個檔案系統—
volume groupSystem + Data + Preboot + Recovery 的組合 ＝ 一個 macOS 安裝hypervisor 要的 14.8.3 需要一整組，不是單一 volume
Preboot存放「主系統掛載前就需要的東西」的 volume，每個安裝一個 UUID 資料夾韌體、開機政策、kernelcache 都在這裡 —— 你要挖 kernelcache 就是去這
stubAsahi 安裝時建的約 2.5GB 迷你 macOS，有殼沒肉、不能開機進去用裡面有韌體 + m1n1 + 開機政策。刪掉 Asahi 就開不了機
ESP（EFI 分割區）FAT32 分割區，掛在 /boot/efi放 GRUB 和 vendorfw/。kernel 不在這裡，在 /boot

開機鏈

名詞是什麼跟你的關係
Boot ROM燒在矽晶片裡的第一棒，永遠不可改信任鏈的根，你碰不到
iBoot 第一階段Apple 韌體，全機共用一份。初始化記憶體、儲存、DFU—
iBoot 第二階段每個 OS 安裝各自一份。載入該 OS 的韌體組、執行它的安全政策這就是為什麼 Asahi 能降安全等級而 macOS 26 不受影響
m1n1Asahi 的開機載入器，被註冊成 stub 那個「OS 的 kernel」現在就在你的開機鏈裡。hypervisor 是它的另一種模式，不是新裝的東西
U-Boot把 Apple 的特殊環境轉成標準 Linux 開機介面（內含 UEFI 實作）—
GRUB讀開機項目清單、顯示選單、載入你選的 kernel動手前先讓它顯示出來，否則新 kernel 開不起來沒地方退回
DFU 模式用另一台 Mac 重刷韌體的救援模式，分兩種： revive 只重刷韌體、保留資料；restore 才會清空整顆硬碟 最後的安全網。先試 revive，restore 是最後手段（所以還是要備份）
ADTApple 自己的 device tree 格式，由 iBoot 提供m1n1 讀它來認機型、抓執行期數值

kernel 與檔案

名詞是什麼跟你的關係
vmlinuz編譯好的 kernel 本體（壓縮過）在 /boot/vmlinuz-<版本>
initramfs開機用的暫時根目錄，讓 kernel 有辦法掛載真正的 rootfs必須在 target 機器上產生，不能在 macOS 上做
device tree一份硬體清單，告訴 kernel「有哪些區塊、在哪個位址、用哪條中斷」ARM 的硬體無法自我介紹，所以必須有人寫下來。DTS 就是逆向成果的存放處
DTBdevice tree 編譯後的二進位檔裝 kernel 一定要連 DTB 一起裝，否則新 driver 永遠不會被實體化
BLS / loader entries/boot/loader/entries/，一顆 kernel 一個 .conf裝完看這裡有沒有多一項 = 最快的驗證
.configkernel 的編譯設定檔，幾千個選項一定要從 /boot/config-$(uname -r) 複製當起點
16K page記憶體分頁大小。TLB 涵蓋範圍大四倍，Apple 硬體照這個設計編錯成 4K 會壞掉 —— 從現有 config 起手就自動正確
fairydustAsahi 的實驗分支，含 USB-C DP 輸出的程式碼官方明說「strictly as-is」，只給開發者、不提供支援。 但 USB-C 出圖只有這裡有 —— #601 的結論就是「換到這個分支就好了」

晶片內部

名詞是什麼跟你的關係
APApplication Processor —— 跑作業系統的主 CPU 核心「AP call」＝ 協處理器反過來呼叫作業系統
協處理器SoC 裡的其他 CPU，各自跑自己的韌體一顆 M1 Pro 裡有十幾顆
DCP顯示協處理器。在 Mac 裡，跑 Apple 韌體，實際操作顯示硬體斷點 2 的對話對象。你只能透過 mailbox 跟它講話
A13在 Studio Display 裡的一整顆 SoC，管面板、hub、攝影機斷點 2 要叫醒的是它，但做這件事的是 DCP，不是你
atcphyType-C PHY，把訊號送上線。driver 直接讀寫它的暫存器斷點 1 的位置（phy/apple/atc.c）。 stable kernel 沒有 DP 這條路，fairydust 有
tipdUSB-PD 控制器，負責協商模式與供電決定協商到 DP Alt Mode 還是 TB
ACIOApple Converged I/O —— Thunderbolt 那組硬體（含 Cortex-M3）路線 B 的核心，Sven 的 22 個 patch 在處理
RTKitApple 協處理器共用的通訊協定已逆向完成，多個 driver 共用
DARTApple 的 IOMMU（記憶體存取保護）已上游，16K 粒度
mailbox / AP callAP 與協處理器之間的雙向訊息機制兩邊都能發起。call 20 是 DCP 問你，不是你問它

「韌體」的三種意思

種類存在哪例子
燒在矽晶片裡不可改，永久Boot ROM
裝置自帶裝置自己的快閃記憶體，可更新但持久Studio Display 的 A13、SSD 控制器
開機時載入平常是磁碟上的檔案，每次開機載進協處理器DCP、WiFi、ACIO

第三種是 Asahi 要從你的 macOS 抓出來的那種，也是「OS-paired firmware」的意思 —— 你的 DCP 韌體來自 macOS 26，跟其他回報者不同。

這個專案的專用說法

名詞意思
t8103 / t600xSoC 代號。t8103 ＝ 原版 M1（你的 mini）；t600x ＝ M1 Pro/Max（你的 MBP）
target被觀測的機器。螢幕插這台，m1n1 和 macOS guest 都在這台
host旁觀者。只跑 Python、收資料、印 trace，不影響 target
DP Alt Mode把 Type-C 的實體通道直接改接成 DisplayPort。不是降級版的 TB，是另一套協定
DSCDisplay Stream Compression，顯示串流壓縮。頻寬不夠時靠它擠出高解析度
斷點 1 / 斷點 2斷點 1 ＝ atcphy 切不進 DP 模式 （已解：換 fairydust，#601 closed）；斷點 2 ＝ DCP 的 call 20 沒人會回 （未解，#579 open）。舊版本頁面稱它們為 Bug 1 / Bug 2
