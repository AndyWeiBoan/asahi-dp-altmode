2026-09-23 晚 ～ 09-24 凌晨 · 第一次動手

從「這份計畫書該怎麼修」開始，結果一路做到外接螢幕點亮。

一句話結論

冷插完全正常；熱插拔畫面回不來，但套了 #622 之後不會再卡住整台電腦。 剩下的卡點在合成器：一個永遠等不到完成的 page flip 把 aquamarine 鎖死了。

做了什麼

  1. 查證計畫書的前提，發現 #601 已在 2026-09-07 結案 —— 原本「兩個 bug、先解 Bug 1」的框架不成立了。 整份計畫書依此改寫，六張圖用 archify 重新產生
  2. 讀完 build 腳本（600 行）。確認 kernel 原始碼是執行時從上游 clone、 .config 抄本機的、README 講的第 9 步在 main() 裡是註解掉的
  3. 跑 build。第一次 --filter=blob:none 的 clone 空等三分鐘零 bytes（GitHub 在算 pack）， 改用 --depth 1 才動。編譯本身 60～90 分鐘
  4. 開機設定：asahi-bless --set-boot fedora（預設不再開進 macOS）、 grubby --set-default 指到 fairydust、把 GRUB 選單叫回來
  5. 第一次插螢幕沒反應 —— 插到左後那孔了。查 device tree 的 connector label 才確認 DP 只在 usb-pd@3f = USB-C Left Front
  6. 換孔，亮了。MSI MAG161V，1920x1080@60，Hyprland 正常接手
  7. 測熱插拔 → 不亮，而且整台卡住幾十秒
  8. 診斷後找到 #622，確認能乾淨套用到現在的 tree
  9. 白做了一輪：中途跑過 git apply -R 把 patch 退掉卻沒發現， 裝上去的是沒 patch 的模組，測出來當然跟原本一樣
  10. 重套、驗證 .ko 裡真的有 patch 的字串、重裝、重測
  11. 結果：不卡了，但畫面還是回不來。追到 hyprland.log 才看清楚原因

也就是 #622 在 t600x 上確實有效，只是沒有把問題解完。 這是目前 #579 上沒有的資料點。

發現了什麼

  • 斷點 1 對這台機器不存在。換到 fairydust 就有 USB-C DP 輸出，不用改任何程式碼
  • DP 只有一個孔（左前），插錯孔完全沒有反應，而且不會有任何錯誤訊息
  • #622 在 t600x 上有效但沒解完：WARNING 和 flip_done timed out 都消失、 不再卡住整台電腦，但熱插拔的畫面仍然回不來。量化數字見上面「量到的東西」
  • 真正的卡點在合成器：一張永遠等不到完成的 page flip，讓 aquamarine 之後拒絕所有 commit （Cannot commit when a page-flip is awaiting，出現 14 次）。 Hyprland 不是沒反應 —— 它有偵測到、有列模式、有嘗試 modeset
  • 單獨跑 make install 會把 /boot/dtb 指歪，這次真的發生了。 只改模組的話根本不需要它
  • 驗證要驗二進位檔。git diff 和時間戳都可能騙人， 要 strings *.ko | grep 確認編出來的東西裡有

沒做到 / 做得不好的地方

  • 整晚幾乎都是「跑腳本、套別人的 patch、看結論」，沒有寫過一行 C，也沒碰過任何暫存器。 這不是計畫的問題 —— 階段 0 本來就不是學習關卡 —— 但要記得它不算數
  • #622 兩塊改動的原理當下沒搞懂，是事後才補寫進手冊 §3 的
  • git apply -R 那一輪白測，浪費約 20 分鐘

明天要幹嘛

  1. 先一起寫一份學習計畫（不是由 Claude 單方面寫完丟過來）
  2. 把兩個 patch 逐行看懂 —— 0001（內建 HDMI resume，11 行，暖身用）和 #622（兩塊，42 行）
  3. 討論熱插拔。重點不只是修好，是搞懂那些探測手段： udevadm monitor、/sys/class/drm、journalctl -k、hyprland.log 各自在講哪一層，輸出怎麼讀
  4. 然後才動 iomfb.c。程式由自己寫，Claude 負責解釋機制、指路、讀結果、review
兩分鐘就能做、但還沒做的事：把 Studio Display 插上去冷開機一次。 到目前為止正主都還沒上場，很可能會看到 acking unhandled call 20 —— 那是跟今天完全不同的一條線（斷點 2），先知道它長什麼樣，排優先順序會比較有依據。
