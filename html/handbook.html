§1操作

怎麼 build、怎麼裝、怎麼退回、更新之後要檢查什麼。全部是照著做就好的東西。

可能不用自己來 —— 而且它的支援表上就有你的機型。 bharambetejas/asahi-fairydust-display 是針對 Fedora Asahi Remix 的一鍵腳本， 支援表把 MacBook Pro M1 Pro 標成「Tested by community」。 它會處理相依套件、Rust、GPU driver、DP alt mode 模組、DTB、m1n1、GRUB、typec 模組自動載入， 還附一個 hotplug 腳本。需要 15GB 空間、60～90 分鐘。

它的 README 也獨立寫了同一件事：「Plug adapter into the FRONT-MOST USB-C port」 —— 跟 dts 裡的 USB-C Left Front 對得上。

它預設會多打一個 patch（修內建 HDMI 在 suspend/resume 後不亮）， 想要原汁原味的分支就 SKIP_PATCHES=1。
讀過腳本之後的三件事。
  • 材料只有 .config 來自本機。原始碼是 git clone AsahiLinux/linux --branch fairydust --filter=blob:none（約 3GB）； .config 則是 cp /boot/config-$(uname -r) —— 所以 16K page 那個坑它自動幫你避開了
  • README 的第 9 步不會跑。main() 裡 setup_display_script 是註解掉的，註解寫「causes login loop on KDE/Wayland」。 對 Hyprland 使用者是好消息 —— 那段會寫一個用 xrandr、 還硬寫死 2560x1600 的腳本（14" 是 3024x1964）， 外加 XDG autostart 和一條 RUN+= 跑 sleep 2 的 udev rule。全部不會發生
  • 它改 GRUB 的那行對你是空轉。它用 sed 's/GRUB_TIMEOUT_STYLE=.*/…/'，只改既有的行； /etc/default/grub 裡沒有這一行的話什麼都不會發生，要自己加
dts 不用 cherry-pick 了。fairydust 分支的 arch/arm64/boot/dts/apple/t600x-j314-j316.dtsi 第 12 行就是 #define ENABLE_DCPEXT_TYPEC，無條件打開；往下 typec1 已經接上 displayport = <&dcpext1>。 也就是 PR #476 想做的事，fairydust 本身就有了。

而且只有一個孔有 DP。那個 connector 的 label 是 "USB-C Left Front" —— 左側靠前那一孔，走 atcphy1。 #601 的回報者也獨立講了同一件事（「only one port carries DP」）。 其餘的孔插了不會有反應，這不是故障。 順帶：atcphy3 在 dts 裡註明 ATC3 is used for DisplayPort -> HDMI only，那是內建 HDMI 孔的專用路徑。
#601 回報者的具體作法（Arch/omarchy，M1 Pro 14"，可直接對照）：
  • .config 直接拿現在跑的那顆（/proc/config.gz）， 他確認需要的符號本來就都開著：CONFIG_DRM_APPLE、CONFIG_PHY_APPLE_ATC、 CONFIG_PHY_APPLE_DPTX、CONFIG_MUX_APPLE_DPXBAR、CONFIG_TYPEC_DP_ALTMODE
  • 裝成獨立的並存 package，stable kernel 留在 GRUB 當退路
  • 冷插比熱插可靠 —— 開機前就把螢幕插著
每次官方 kernel 更新，都會把 /boot/dtb 搶回去 —— 這是最容易中招的一點。

Fedora 的 /usr/lib/kernel/install.d/10-devicetree.install 在每次 kernel add 時會無條件做這件事： 
rm -f /boot/dtb
ln -s dtb-$KERNEL_VERSION /boot/dtb
它掃的是 /boot/dtb-*（連字號）， 而 make dtbs_install 把 fairydust 的 DTB 裝到 /boot/dtbs/<版本>（複數、斜線）—— 兩者對不上，所以 fairydust 的 DTB 對那支 hook 是隱形的。 緊接著 15-update-m1n1.install 會跑 update-m1n1 把官方 DTB 刷進去。

結果：omarchy update 帶進一顆新官方 kernel 之後， 你的 fairydust kernel 會帶著官方 DTB 開機 —— ENABLE_DCPEXT_TYPEC 那些節點不見了，外接螢幕安靜地不再亮。 症狀是「明明沒動什麼，某天就壞了」。

檢查與修復： 
readlink /boot/dtb          # 指到 dtb-…asahi… 就是被搶走了
sudo ln -sfn /boot/dtbs/<fairydust 版本> /boot/dtb
sudo update-m1n1
值得做成 omarchy 的 post-update hook，跟你其他那幾個放在一起。
另外兩件關於 omadora 的事。
  • installonly_limit 管不到它。 那個限制只作用在 RPM 標記為 installonly 的套件；腳本走的是 make install， 裝出來的不是 RPM，dnf 不會把它擠掉。 （會被擠掉的是最舊那顆官方 kernel。）
  • omarchy update 不會幫你重 build fairydust，上游有新 commit 要自己重跑
它動到的全域設定只有一個，而且退回 stable 也吃得到。 就是上面那個 /boot/dtb + update-m1n1 —— m1n1 之後每次開機都帶著 fairydust 的 device tree，包括你在 GRUB 選回官方 kernel 那次。 其餘（模組、DTB、vmlinuz、initramfs）都帶 -fairydust 後綴並存，不覆蓋任何東西。

repo 裡的 asahi-fairydust-uninstall.sh 會把這些全部還原， 包含把 /boot/dtb 指回官方版本再跑一次 update-m1n1。 它會擋你在 fairydust kernel 裡執行，要先重開機回官方 kernel。

只改模組的時候不要跑 make install

改動只在 *.ko（例如只動了 iomfb.c 或 atc.c）的話， 不需要重裝 kernel 本體，也就不會觸發那個把 /boot/dtb 指歪的 hook： 

cd ~/linux-fairydust
make -j8                                    # 增量，約 40 秒
strings drivers/phy/apple/phy-apple-atc.ko | grep 'park PIPE handler'   # 驗證
sudo make INSTALL_MOD_STRIP=1 modules_install
sudo dracut -f --kver 7.1.13-fairydust+
readlink -f /boot/dtb                       # 要是 /boot/dtbs/7.1.13-fairydust+
sudo reboot

退回與移除

  • 暫時退回：重開機，在 GRUB 選 7.1.13-402.asahi.fc44.aarch64+16k。 官方 kernel 完全沒被動過
  • 退掉某個 patch： cd ~/linux-fairydust && git apply -R ~/dev/asahi-fairydust-display/patches/<檔名>， 然後照上面那組重編重裝。退完記得也把 patches/ 裡那個檔移走， 否則下次跑 build 腳本又會自動套回去
  • 完全移除：~/dev/asahi-fairydust-display/asahi-fairydust-uninstall.sh。 它會把 kernel、模組、DTB、/boot/dtb、m1n1 全部還原， 但要先重開機回官方 kernel 才跑得動

hyprland.log 是最容易被忘記、但最常給出答案的那一個。 2026-09-24 那次熱插拔，前面四個工具都顯示「一切正常」， 只有它講出真話：Cannot commit when a page-flip is awaiting。

怎麼分辨是 kernel 的問題還是 Hyprland 的問題

你的 MBP 跑 Hyprland，這會製造一種很容易誤判的情況：kernel 其實已經把螢幕接起來了，但畫面就是沒出來。 這不是假設 —— PR #622 的作者就留了這個已知問題： 「重新接上之後，userspace 沒有對 BAD link status 做出反應，要手動 toggle output」。那是合成器層，不是 kernel。

所以每次測試都照這個順序查，對應圖 1 的層次：

# ① kernel 有沒有看到這個接頭？
ls /sys/class/drm/
cat /sys/class/drm/*/status          # connected / disconnected

# ② 有沒有拿到 mode？
cat /sys/class/drm/card*/*/modes

# ③ 合成器有沒有接手？
hyprctl monitors all
wlr-randr

# ④ 底層在講什麼
dmesg | grep -iE 'dcp|atcphy|tipd|typec|altmode'
① connector② modes③ Hyprland結論
disconnected——卡在斷點 1（atcphy，訊號沒出去）—— 先確認你用的是 fairydust、插的是左前那一孔、而且是冷插
connected空的—卡在斷點 2（DCP 沒給 mode）
connected有 mode沒看到Hyprland 沒接手，kernel 那邊其實通了
connected有 mode看得到、還說 enabled 但畫面還是黑的 —— 這一種 2026-09-24 實際撞到了，見日誌。 去看 hyprland.log 找 Cannot commit when a page-flip is awaiting

第三種是好消息 —— 代表你已經穿過兩個斷點了，剩下的是 userspace 設定。 第四種最難認，因為每一層都回報「我沒問題」。

用到的診斷指令（下次可以照抄）

# kernel 看到什麼
cat /sys/class/drm/*/status
wc -l < /sys/class/drm/card2-DP-1/modes

udevadm monitor --udev --subsystem-match=drm

# 合成器怎麼想的 —— 這個最容易被忘記，但這次是它給出答案
tail -f $XDG_RUNTIME_DIR/hypr/*/hyprland.log

wlr-randr
ls -d /sys/class/typec/port*-partner

for c in /proc/device-tree/soc/*/*/connector; do
  echo "$(basename $(dirname $c)): $(tr -d '\0' < $c/label)"
done

這顆 kernel 上到底疊了哪些東西

三層，容易搞混，先分清楚 —— 只有第三層是這次為了熱插拔加的：

是什麼誰做的跟外接螢幕的關係
底層 fairydust 分支本身 Asahi 上游的實驗分支 USB-C 出圖的程式碼全部在這裡。正式 kernel 沒有，所以非用不可
patch 0001 0001-drm-apple-reconnect-DP2HDMI-output-on-resume.patch build 腳本作者自己加的（原作者 rgvxsthi） 無關。它修的是內建 HDMI 孔睡醒之後不亮，走的是另一條路徑。 跟著腳本一起來的附贈品，SKIP_PATCHES=1 可以不要
patch 0002 0002-pr622-fix-dp-altmode-hotplug.patch（= PR #622） 這次自己加的 這才是這一節在講的東西，修 USB-C DP 的熱插拔

換句話說「fairydust 是分支，不是 patch」；而 0001 雖然跟著 fairydust 的 build 腳本一起來， 但它不是 fairydust 的一部分，也跟 USB-C 沒關係。下面所有的 before/after 都只在講 0002。

#622 到底改了什麼（白話版）

它只改兩個檔、42 行，但是兩個完全不同的問題。

第一塊 · iomfb.c —— 為什麼會卡住幾十秒

先講「page flip」是什麼：合成器每畫好一張畫面，就交給 kernel 說「換成這張」， 然後停下來等 kernel 回報「換好了」才畫下一張。這是正常運作方式。

問題在於，螢幕剛接上、DCP 還沒真正把顯示管線開起來的那段時間 （driver 裡那個旗標叫 valid_mode，這時候是 0）， DCP 會收下那張畫面然後默默丟掉，不回報。firmware 自己的 log 寫得很直白： 

swap_submit_dcp: swallowed swap ID 452 as fControllerPowerState is 0
swap_submit_dcp: swallowed swap ID 452 as timings are not enabled

合成器不知道畫面被丟了，就一直等，直到內建的 10 秒逾時。 它想畫幾張就卡幾個 10 秒 —— 這就是「整台電腦卡住幾十秒」的來源。

patch 做的事：送出去之前先看一眼 valid_mode。 還是 0 就別送了，直接自己標記「這一幀完成」讓合成器繼續跑下去。三行： 

if (!dcp->valid_mode) {
        schedule_work(&dcp->vblank_wq);
        return;
}

注意這不是「修好顯示」，是「不要因為顯示還沒好就把整台機器拖住」。 差別很重要 —— 它解釋了為什麼套完之後不卡了，但畫面依然沒出來。

第二塊 · atc.c —— 為什麼熱插不會亮、冷插卻會

USB-C 那條線裡有幾組高速通道，同一組實體線路可以拿來跑 USB3，也可以拿來跑 DisplayPort， 兩者互斥。要從 USB3 切成 DP，得先把負責 USB3 的那個電路（叫 PIPE handler）停下來， 否則就是在一條還在通電的線路底下重新接線 —— 硬體會保護性地退回只剩 USB2，DP 根本起不來。

這就是冷插會動、熱插不會動的原因。 開機時就插著的話，那時 USB3 還沒起來，沒有東西要停； 熱插的時候 USB3 已經在跑了，才會撞到。

原本的程式碼發現「PIPE handler 還開著」時，只是印一個警告然後硬切 —— 那正是你在 dmesg 看到的： 

WARNING: drivers/phy/apple/atc.c:2328 at atcphy_mux_set+0x138/0x230 [phy_apple_atc]

patch 做的事：把那個「只抱怨不處理」換成真的去處理 —— 切換前先把 PIPE handler 停到一個空的 dummy PHY 上，讓線路安靜下來，再切模式。 USB3 會暫時斷掉（等 dwc3 重新設定回來），USB2 不受影響。

驗證方式：strings phy-apple-atc.ko | grep 'park PIPE handler'。 有這個字串才代表模組是打過 patch 的（見下面「踩到的坑」）。

剩下的問題：一個卡死的 page flip

套完 #622 之後，熱插拔的失敗鏈條變成這樣：

  1. 拔線那一刻，DCP 吞掉一張 page flip，永遠不回報完成
  2. aquamarine（Hyprland 的 DRM 後端）那張 flip 就一直掛在「等待中」
  3. 之後每一次 commit 都被它自己的保護擋掉 —— hyprland.log 裡 Cannot commit when a page-flip is awaiting 出現了 14 次
  4. 連手動用 wlr-randr 強制 modeset 都救不回來： kernel 那邊確實跑完了（set_digital_out_mode finished:8162）， 但畫面 commit 進不去

關鍵是 Hyprland 並不是「沒反應」。它的 log 顯示它有偵測到、有列出 16 個模式、也有嘗試 modeset： 

drm: Connector DP-1 connected
drm: Modesetting DP-1 with 1920x1080@60.00Hz
ERR: drm: Cannot commit when a page-flip is awaiting
層可以說是它的問題的地方
kernel / driver DCP 收下 page flip 卻從不送完成事件。#622 讓「等待」不再卡 10 秒， 但遺失的 flip 在合成器那邊的帳沒有被清掉
Hyprland / aquamarine 一旦有 flip 卡住，就再也不接受任何 commit，沒有逾時、沒有復原路徑。 硬體丟事件是常態，合成器不該因此永久鎖死一個輸出

兩邊都有道理，所以先別急著替誰定罪 —— 這正是值得寫進 issue 讓真正懂的人判斷的東西。

§4踩過的坑

這一輪踩到的四個坑

1 · 插錯孔，什麼都不會發生。 只有 USB-C Left Front 有 DP（/sys/class/typec/port1，i2c 位址 0-003f）。 對照表可以自己讀出來： 
for c in /proc/device-tree/soc/*/*/connector; do
  echo "$(basename $(dirname $c)): $(tr -d '\0' < $c/label)"
done
結果是 usb-pd@38 = Left Back、usb-pd@3f = Left Front、usb-pd@3b = Right。 插對之後，ls /sys/class/typec/port*-partner 會出現 port1-partner。
2 · 單獨跑 make install 會把 /boot/dtb 指歪。 這次真的發生了：symlink 變成指向不存在的 /boot/dtb-7.1.13-fairydust+ （實際檔案在 /boot/dtbs/7.1.13-fairydust+），然後 update-m1n1 拿著這個斷掉的路徑去刷。 原因見本頁 §1 的那個警告。

只改模組的話根本不需要 make install，用這組就好，順便繞開整個問題： 
sudo make INSTALL_MOD_STRIP=1 modules_install
sudo dracut -f --kver 7.1.13-fairydust+
readlink -f /boot/dtb        # 確認還是 /boot/dtbs/7.1.13-fairydust+
3 · patch 被退掉了卻沒發現，白測一輪。 中途跑過 git apply -R，之後 build 出來的模組其實沒有 patch， 測試結果自然跟沒改一樣。安裝前一定要驗證二進位檔本身： 
strings drivers/phy/apple/phy-apple-atc.ko | grep 'park PIPE handler'
光看 git diff 或檔案時間戳不夠 —— 要確認編出來的東西裡面有。
4 · hyprctl dispatch 在 Lua 設定下要換寫法。 hyprctl dispatch dpms off DP-1 會被 Lua 剖析器拒絕。 這次繞過去的辦法是直接用 wlr-randr（走 Wayland 協定，不經過 Hyprland 的設定層）： 
wlr-randr --output DP-1 --off && sleep 1 && wlr-randr --output DP-1 --on
（這次它成功逼出了 modeset，但因為上面那個 page flip 卡死，畫面還是沒回來。）

§5開機鏈：每個角色在做什麼

這一節是階段 0 的前置知識。你要多裝一顆 kernel、要能在兩顆之間切換、 之後還要讓 m1n1 換個模式跑 —— 這些都建立在「開機時到底發生什麼」之上。

圖 5 · 開機鏈在新分頁開啟，可全螢幕操作 ↗

上排是平常開機的五棒，下排是 m1n1 的另一種用法 —— 分歧點就在第二棒。

五棒接力

角色做什麼
iBootApple 的韌體。驗證簽章後交棒，你完全碰不到
m1n1初始化硬體、產生 device tree。Asahi 安裝時就放進 stub 分割區了
U-Boot把 Apple 的特殊開機環境轉成標準的 Linux 開機介面
GRUB讀開機項目清單、顯示選單、把你選的那顆 kernel 載進記憶體
Linux kernel掛載 rootfs、載入模組，最後交給 systemd → Hyprland

kernel 是一組帶版本後綴的檔案

所以多顆可以並存 —— 裝新的不會蓋掉舊的：

/boot/vmlinuz-<版本>              # kernel 本體
/boot/initramfs-<版本>.img        # 開機用的暫時根目錄
/boot/dtb-<版本>/                 # device tree（Asahi 必要，別忘了裝）
/lib/modules/<版本>/              # 驅動模組

那份「有哪些 kernel 可以選」的清單

Fedora 用 BLS（Boot Loader Specification）：一顆 kernel 一個設定檔。

ls /boot/loader/entries/     # 每個 .conf 就是選單上的一項
sudo grubby --info=ALL       # 人話版：列出每一項的 kernel / initrd / 參數

裝完 fairydust 之後這裡會多一項 —— 那是「有沒有裝成功」最直接的驗證，比重開機試快得多。

動手 build 之前，先讓 GRUB 選單顯示出來。 Asahi 預設會跳過選單（為了開機快）。編輯 /etc/default/grub， 把 GRUB_TIMEOUT 設成 5，同時確認 GRUB_TIMEOUT_STYLE=menu —— 只改 timeout 而 style 還是 hidden 的話選單照樣不會出現。 然後 sudo grub2-mkconfig -o /boot/grub2/grub.cfg。

不先做這件事，新 kernel 開不起來時你會找不到地方選回舊的。

m1n1 不是要新裝的東西

它現在就在你的開機鏈裡，每次開機都在跑 —— 沒有它 Asahi 根本開不起來。 之後要做的不是安裝新程式，而是讓同一支程式換個模式：

模式做什麼
平常（你現在）初始化硬體 → 交棒給 U-Boot → 一路到 Linux
hypervisor（之後）進 EL2、攔截 MMIO、把 macOS 當 guest 開起來

實務上會有兩份 m1n1 並存：stub 裡那份繼續負責開你的 Asahi； hypervisor 用的是你自己 build 的新版（官方文件強調「每次都先 chainload working tree 的 m1n1」）。 兩份互不干擾，正常開機流程不受影響。

「韌體」的三種意思

種類存在哪例子
燒在矽晶片裡不可改，永久Boot ROM
裝置自帶裝置自己的快閃記憶體，可更新但持久Studio Display 的 A13、SSD 控制器
開機時載入平常是磁碟上的檔案，每次開機載進協處理器DCP、WiFi、ACIO

第三種是 Asahi 要從你的 macOS 抓出來的那種，也是「OS-paired firmware」的意思 —— 你的 DCP 韌體來自 macOS 26，跟其他回報者不同。
